ПОДТВЕРЖДЁННЫЕ ОСНОВАНИЯ
1. Категории выглядят одинаково, но действуют по-разному: data-category фильтрует #selection, data-request сразу добавляет направление и ведёт к #contact; нейтральное оборудование ведёт в отдельный раздел. Пользователь не может предсказать результат по карточке.
2. После девяти категорий идут ещё три карточки типов оборудования с повторяющимися изображениями и затем несколько блоков про подбор, совместимость и согласование. Содержание полезно, но в композиции слишком много повторений одинаковой важности.
3. Крупные заголовки почти повсеместно используют weight800, одинаковые двухстрочные конструкции и общую модель section-heading. Важность выбора, проектирования и вспомогательной информации различается недостаточно.
4. Иллюстрации согласованы по цвету, однако преимущественно показывают похожие идеальные кухни. Они создают атмосферу, но не объясняют, какой конкретно результат получает покупатель.
5. Максимальный hero-ресурс — 1600×900; исходник — 1672×941. Этого недостаточно для нативной детализации полноширинного изображения на 2560px. Создание файла 3200px из этого исходника не добавит реальных деталей.
6. Доверие выражено в основном текстом и внешней ссылкой на отзывы. На самой странице нет проверяемого примера спецификации, процесса принятия решения или выполненного проекта. Это ограничение контента, а не основание придумывать доказательства.
7. На телефоне девять высоких категорий и три карточки выбора сильно растягивают первый этап знакомства. Исправляй плотность и повторения, сохраняя читаемость и зоны нажатия.

Сформируй responsive assets: hero 640/1024/1600/2560(3200 при обосновании), предметы 400/800, сцены 640/1200/1600 по фактическому месту. WebP/AVIF с fallback; srcset/sizes соответствуют реальной сетке.
У всех изображений заданы width/height или aspect-ratio. LCP-изображение не lazy, остальные lazy. Не загружай все full-resolution исходники в мобильный первый экран.
Сохрани provenance и prompts при генерации. Оборудование без подтверждённой модели обозначается как иллюстрация типа, а не товарная карточка конкретного SKU.

11. АНИМАЦИЯ И МИКРОВЗАИМОДЕЙСТВИЯ
Сохрани один motion-словарь: easing cubic-bezier(.22,1,.36,1); цвет/подчёркивание 120–180ms; кнопки 160–220ms; панели 220–280ms; первое появление hero 500–700ms.
Это ориентиры. Не замедляй уже понятные действия ради эффекта. Не добавляй глобальные reveal, задерживающие чтение каждой секции.
Кнопка: фиксированная геометрия, смена поверхности/цвета, необязательный сдвиг стрелки 2–3px. Никаких прыгающих размеров, магнитного курсора и бегущего блика.
Категория: мягкое изменение рамки/поверхности; предмет увеличивается максимум 1.02 при точном указателе. Фокус виден независимо от hover. На touch нет зависимости от наведения.
Меню: opacity +translateY на 4–6px без смещения основного layout. Закрытие немного быстрее открытия. Следи, чтобы быстрые повторные действия не оставляли невидимый слой, перехватывающий клики.
При prefers-reduced-motion отключи вступительные движения, zoom и программный плавную прокрутку. Сохрани понятные мгновенные состояния и фокус. Не используй scrolljacking, автокарусели, фоновое autoplay видео и бесконечный parallax.

12. ДОСТУПНОСТЬ, АДАПТАЦИЯ И ПРОИЗВОДИТЕЛЬНОСТЬ
Проверка viewport: 2560×1440, 1920×1080, 1440×900, 1366×768, 1024×768, 768×1024, 390×844, 360×800, 320×740, 844×390; отдельно границы 1199/1200, 900/901, 700/701.
При ширине 320px нет горизонтального overflow; при 200% zoom доступны текст, навигация и форма. Проверяй reflow при эффективной ширине 320 CSS px. Не скрывай контент, чтобы тест стал зелёным.
Контраст обычного текста ≥4.5:1, крупного ≥3:1; значимые границы контролов и индикаторы фокуса проверяй по WCAG 2.2. Контраст на фотографии измеряй в реальном кропе.
Для основных кнопок цель 44×44px или больше; это усиленный проектный стандарт удобства, а не пересказ AA-минимума 24×24px с его исключениями.
Семантические h1–h3, настоящие button для действий, ссылки для переходов, labels для полей, корректный порядок Tab. Не используй цвет как единственный признак выбора.
Бюджет разработки: не ухудшить размер JS и LCP после новых изображений. Цели Core Web Vitals для реальных пользователей: LCP≤2.5s, INP≤200ms, CLS≤0.1 на 75-м перцентиле. Локальный Lighthouse или Playwright не подменяет полевые измерения.
Измерения делай после загрузки шрифтов, валидных изображений и со стабильной композицией. Перед full-page screenshot прокрути страницу для отрисовки lazy-изображений; пустой offscreen-слой compositor не объявляй поломкой сайта без проверки в viewport.

13. ПЛАН РЕАЛИЗАЦИИ И ПРИЁМКА
Сначала исправь предсказуемость категорий и перекрытие результата панелью подборки; затем сократи дублирование и структурируй главы; затем собери наглядный разбор решения; после этого настрой типографику, изображения, форму и микродвижение.
До UI-правок зафиксируй исходные скриншоты desktop, mobile и меню. После основной реализации проведи один общий визуальный проход, исправь обнаруженное одним пакетом, выполни подтверждение.
Обязательные сценарии: открыть/закрыть меню мышью, клавиатурой и тач; найти категорию; просмотреть категорию без добавления; добавить/удалить направление; очистить подборку; выбрать формат; сохранить черновик; вызвать ошибку в контакте; подготовить запрос; изменить данные и пересобрать запрос; проверить fallback копирования; скачать текст и чек-лист.
Прогони npm run check и npm run build, проверь отсутствие ошибок консоли, битых изображений, двойных обработчиков и фокусных ловушек. Тесты должны проверять поведение, а не повторять CSS в виде утверждений.
Визуальные критерии приёмки: видны главный выбор и главный пример; разделы имеют разный вес; вспомогательные тексты не конкурируют с заголовками; страница не состоит из одинаковых карточек; все изображения выдерживают масштаб 100%; переходы спокойные; мобильная страница не повторяет ненужные десктопные объёмы.
В итоге выдай: изменённый код, скриншоты до/после, короткое пояснение пяти ключевых решений, результаты проверок, список недостающих реальных материалов. Обнови DESIGN.md по фактическому результату.
